# Товародвижение · BI

Прототип BI-приложения на Streamlit для продуктовой розницы: продажи, промо, запасы и пополнение, логистика, качество и потери, прогноз, AI-помощник и самообслуживание.

| Версия | Ссылка | Ветка | Что это |
|---|---|---|---|
| **2** (текущая) | https://retail-bi-v2.streamlit.app/ | `v2` | Прототип по функциональным требованиям заказчика: роли и доступ, конструктор отчётов, прогноз, AI-помощник, уведомления, библиотека KPI, экспорт в 5 форматов |
| 1 | https://app-bi-jbpazcgjfwtjmhtebvab9h.streamlit.app/ | `main`, `v1` | Первый MVP: обзор сети, data story, продажи, ABC/XYZ, запасы, логистика |

В боковой панели каждой версии есть кнопка перехода на другую. Адреса задаются секретами `V1_URL` и `V2_URL` (по умолчанию — адреса из таблицы).

> **Данные синтетические.** Структура двух сетей (около 100 супермаркетов «у дома» и около 860 дискаунтеров, 7 РЦ, регионы, темпы открытий, параметры промо и лояльности) взята из открытых источников. Продажи, остатки, поставки, рейсы, брак и сертификаты сгенерированы моделью и не отражают реальные результаты компаний. РЦ в Туле и деление на федеральные округа, дивизионы и УГМ — допущения прототипа. Источники и допущения — на странице «О данных и методика» и в `bi/config.py`.

**Что сознательно не сделано в прототипе** (требует целевой платформы или инфраструктуры заказчика): вход через SSO / Active Directory, отправка уведомлений в e-mail, Telegram, MAX, Битрикс24, рассылка по расписанию, загрузка из реальных источников и ETL, drag-and-drop размещение блоков, генеративный AI-помощник для формул, offline-режим. Демо-роли выбираются в боковой панели — это демонстрация модели прав, а не защита данных.

Состояние приложения (наборы фильтров, отчёты, комментарии, правила, журнал) хранится в SQLite рядом с данными и общее для всех пользователей экземпляра. На Streamlit Community Cloud оно сбрасывается при перезапуске приложения.

## Запуск локально

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
streamlit run app.py
```

При первом запуске генерируются данные (~10 секунд, около 150 МБ в `data/generated/`).

## Публикация ссылкой (Streamlit Community Cloud)

Каждая версия — отдельное приложение из своей ветки:

1. Войдите на [share.streamlit.io](https://share.streamlit.io) через GitHub.
2. **Create app** → репозиторий `Gladun-D/streamlit-bi`, ветка `v2` (для версии 1 — `main`), файл `app.py`.
3. **App URL** — например `retail-bi-v2`. В **Advanced settings** выберите Python 3.12.
4. **Deploy**. Через 3–5 минут приложение доступно по ссылке.
5. Если адрес отличается от `retail-bi-v2.streamlit.app`, добавьте в **Settings → Secrets** обеих версий строку `V2_URL = "https://<адрес>.streamlit.app/"`, чтобы кнопки перехода вели на верный адрес.

## Развёртывание на своём сервере

```bash
docker build -t retail-bi .
docker run -d -p 8501:8501 --name retail-bi retail-bi
```

Для нескольких сотен одновременных пользователей нужно несколько реплик за балансировщиком с «липкими» сессиями (Streamlit держит сессию по WebSocket), вход через корпоративный SSO на уровне обратного прокси и хранение состояния приложения во внешней БД вместо SQLite.

## Источник данных

По умолчанию — встроенный DuckDB поверх parquet-файлов. Подключение MySQL / MariaDB:

```bash
python scripts/load_mysql.py --url "mysql+pymysql://user:pass@host:3306/retail_bi?charset=utf8mb4"
```

Полная загрузка (~10 млн строк) занимает 15–30 минут; для быстрой проверки можно загрузить только свежие данные: `--since 2026-09-01`. Затем в `.streamlit/secrets.toml` (пример — `.streamlit/secrets.toml.example`) или в переменных окружения:

```toml
DATA_BACKEND = "mysql"
MYSQL_URL = "mysql+pymysql://user:pass@host:3306/retail_bi?charset=utf8mb4"
```

Другие СУБД подключаются через SQLAlchemy: `DATA_BACKEND = "sql"` и `SQL_URL` (нужен драйвер; SQL проверен на DuckDB и MariaDB 10.11, для PostgreSQL, ClickHouse и MS SQL его нужно проверить под диалект). Агрегация выполняется на стороне базы; для реальных данных достаточно заполнить те же таблицы или представления — код страниц менять не нужно.

## Структура

```
app.py                 точка входа: роль, навигация, общие фильтры, ссылка с фильтрами
bi/config.py           параметры сетей, оргструктура, источники, допущения, версии
bi/synth.py            генератор синтетических данных (seed фиксирован)
bi/db.py               источники данных: DuckDB / MySQL / SQLAlchemy
bi/queries.py          запросы с кэшированием (отчёты — 1 час, оперативные — 15 минут), фильтры и RLS
bi/access.py           роли, страницы и ограничения данных
bi/state.py, seed.py   состояние приложения (SQLite) и демо-наполнение
bi/kpi.py              библиотека показателей и безопасный вычислитель формул
bi/forecast.py         модели прогноза, бэктест и точность
bi/ai.py               аномалии, выбросы, тренды, факторы, сценарии «что если»
bi/alerts.py           правила уведомлений и история срабатываний
bi/export.py           выгрузка в Excel, CSV, XML, PDF, PowerPoint
bi/metrics.py          формулы показателей (без Streamlit, покрыты тестами)
bi/ui.py, docs.py      оформление, KPI-карточки, графики, описания отчётов
views/                 страницы приложения
static/topojson/       карта мира для графиков (без обращения к CDN)
scripts/load_mysql.py  загрузка данных в MySQL
tests/                 тесты формул, модулей v2 и отрисовки всех страниц под разными ролями
```

Тесты: `pip install -r requirements-dev.txt && pytest -q`.

## Ограничения прототипа

- Точность прогнозов на синтетических данных завышена: ряды гладкие. На реальных данных ошибка на уровне магазина и SKU будет заметно выше.
- Продажи магазинов детализированы до категории в день; уровень SKU — на складах и в детализации по долям. Детализация «товар – день – магазин» требует агрегированных витрин в DWH.
- Формулы — типовые отраслевые; в рабочей версии их нужно привести к методологии компании.
- Ценовая эластичность в сценариях «что если» — допущение по категориям, а не оценка по данным.
