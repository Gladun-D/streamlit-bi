# Товародвижение · BI
## https://app-bi-jbpazcgjfwtjmhtebvab9h.streamlit.app/

> Это **версия 1** (ветки `main` и `v1`). **Версия 2** — прототип по функциональным требованиям заказчика: https://retail-bi-v2.streamlit.app/ (ветка `v2`). В боковой панели каждой версии есть кнопка перехода на другую.
MVP BI-приложения на Streamlit для продуктовой розницы: продажи, запасы и пополнение, логистика, ABC/XYZ-анализ и data story для руководителя, категорийного менеджера, логиста и аналитика.

> **Данные синтетические.** Структура двух сетей (около 100 супермаркетов «у дома» и около 860 дискаунтеров с 5 РЦ, регионы, темпы открытий, параметры промо и лояльности) взята из открытых источников. Продажи, остатки, поставки и рейсы сгенерированы моделью и не отражают реальные результаты компаний. Источники и допущения перечислены в приложении на странице «О данных и методика» и в `bi/config.py`.

## Что внутри

| Страница | Для кого | Что показывает |
|---|---|---|
| Обзор сети | руководитель | KPI к прошлому году и плану, LFL, тренд, сравнение сетей, светофор по РЦ и регионам, магазины и категории, требующие внимания |
| Data story | руководитель, аналитик | Что произошло → почему → прогноз и сценарии «что если» → выводы; тексты собираются из расчётов |
| Продажи | категорийный менеджер, аналитик | Факторы выручки (трафик и чек), профиль недели, структура и LFL категорий, промо и его эффект, онлайн-доставка, рейтинг магазинов |
| Ассортимент ABC/XYZ | категорийный менеджер | Матрица ABC × XYZ, кривая Парето, рекомендации по группам, выгрузка |
| Запасы и пополнение | логист, категорийный менеджер | Покрытие, дефицит, излишки, неликвид, тепловая карта регион × категория, страховой запас, точка заказа и рекомендуемый заказ |
| Логистика | логист | OTIF и сроки поставщиков, пунктуальность рейсов склад → магазин, почасовой профиль, потери |
| О данных и методика | все | Источники, допущения, модель данных, формулы, проверки качества данных |

Общие фильтры в боковой панели работают на всех страницах: период, сеть, склад/РЦ, регион, магазин, категория. Списки зависят друг от друга. Таблицы выгружаются в Excel, графики — в PNG (кнопка камеры над графиком).

## Запуск локально

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
streamlit run app.py
```

При первом запуске генерируются данные (~15 секунд, около 150 МБ в `data/generated/`).

## Публикация ссылкой (Streamlit Community Cloud)

1. Войдите на [share.streamlit.io](https://share.streamlit.io) через GitHub.
2. **Create app** → репозиторий `Gladun-D/streamlit-bi`, ветка `main`, файл `app.py`.
3. В **Advanced settings** выберите Python 3.12.
4. **Deploy**. Через 2–4 минуты появится ссылка вида `https://<имя>.streamlit.app`.

Приложение из публичного репозитория доступно всем, у кого есть ссылка. После долгого простоя оно «засыпает» и просыпается по кнопке за минуту.

## Развёртывание на своём сервере

```bash
docker build -t retail-bi .
docker run -d -p 8501:8501 --name retail-bi retail-bi
```

Для нескольких сотен одновременных пользователей нужно несколько реплик за балансировщиком с «липкими» сессиями (Streamlit держит сессию по WebSocket) и вход через корпоративный SSO на уровне обратного прокси.

## Источник данных

По умолчанию — встроенный DuckDB поверх parquet-файлов. Подключение MySQL:

```bash
python scripts/load_mysql.py --url "mysql+pymysql://user:pass@host:3306/retail_bi?charset=utf8mb4"
```

Полная загрузка (~10 млн строк) занимает 15–30 минут; для быстрой проверки можно загрузить только свежие данные: `--since 2026-09-01`. Проверено на MariaDB 10.11 (совместима с MySQL по используемому SQL): цифры совпадают со встроенной базой.

Затем в `.streamlit/secrets.toml` (пример — `.streamlit/secrets.toml.example`) или в переменных окружения:

```toml
DATA_BACKEND = "mysql"
MYSQL_URL = "mysql+pymysql://user:pass@host:3306/retail_bi?charset=utf8mb4"
```

SQL приложения написан на общем подмножестве и одинаково работает в DuckDB и MySQL; агрегация выполняется на стороне базы. Для реальных данных достаточно заполнить те же таблицы (или представления с теми же именами и полями) — код страниц менять не нужно.

## Структура

```
app.py                 точка входа: навигация, общие фильтры
bi/config.py           параметры сетей, источники, допущения
bi/synth.py            генератор синтетических данных (seed фиксирован)
bi/db.py               источники данных: DuckDB / MySQL
bi/queries.py          запросы с кэшированием (st.cache_data, TTL 1 час)
bi/metrics.py          формулы показателей (без Streamlit, покрыты тестами)
bi/ui.py               оформление: KPI, графики, форматирование, выгрузка
views/                 страницы приложения
scripts/load_mysql.py  загрузка данных в MySQL
tests/                 тесты формул и отрисовки всех страниц
```

Тесты: `pip install -r requirements-dev.txt && pytest -q`.

## Ограничения MVP

- Продажи магазинов детализированы до категории; уровень SKU показан на складах. Детализация «товар – день – магазин» требует агрегированных витрин в БД.
- Формулы — типовые отраслевые; в рабочей версии их нужно привести к методологии компании.
- Прогноз — сезонный наивный метод (ориентир, а не план); сценарии — упрощённые модели с явными допущениями.
- Нет авторизации и разграничения прав: в рабочем контуре это делается на уровне прокси и SQL-фильтров.
